Lensify

Single-scan adaptive project lens plus a token-optimized context capsule for any AI coding agent. Turns any codebase into a one-page summary your agent ingests in 800–3,600 tokens instead of reading 30+ files.

30 framework adapters
4 distribution channels
527 tests + 17 perf budgets
70–90% orientation tokens saved

What is Lensify

Lensify is a plugin that scans a codebase once and produces two artefacts:

LENS.html

For humans · single page · 30-second read

A self-contained HTML page with five panels: what the project is, the architectural picture, a day-1 narrative, hotspots, and risks & unknowns. Drop it on someone's screen and they understand the project before their next sip of coffee.

LENS.capsule.md

For agents · 800–3,600 tokens · token-bounded

A Markdown context block your AI agent ingests instead of reading 30+ raw files. Framework-aware sections surface the structural skeleton: routes, models, training loops, vector indexes, agents, graphs, deployments.

It also ships five session hooks (in Claude Code) that compound across a long session: read deduplication, activity tracking, selective context injection, output compression, and cross-session memory.

And a conversation compactor (/lensify compact) that reclaims 8–25k tokens mid-session by generating a WORKING_CONTEXT.md you load after /clear.

Why it exists

Modern AI agents have a context-window problem: the bigger the project, the more tokens they burn just orienting. A typical onboarding flow reads 20–40 files before the agent can do useful work. That's 10–30k tokens spent on understanding, not solving.

Lensify replaces that with a single 30-second scan. The agent reads one capsule instead of dozens of files. Token usage drops 70–90% just from orientation savings — and the rest of the hook system stacks more savings on top of that.

The headline trade-off: deterministic structural extraction (fast, free, framework-aware) vs. semantic vector search (slower, embedding cost, generic). Lensify does the first. It works alongside semantic tools like Cursor's @codebase, not against them.

How it works

The scan engine runs five phases per invocation:

Phase What it does Output
1. Walk Respects .gitignore + vendor exclusions. Categorises every file as code/doc/meta. File inventory
2. Parse Python via stdlib ast. JS/TS/Go/Java via regex. Captures imports + symbols. Per-file metadata
3. Tier Picks T1/T2/T3 from file count, LOC, top-level dirs, monorepo markers. Token budget
4. Adapt Lazy-loads matching framework adapters via manifest. Each emits a typed section. Framework records
5. Render Composes the capsule under tier budget. Writes HTML lens. Caches the result. Capsule + HTML

Total typical runtime: 30 ms (medium) to 113 ms (500 files).

Installation

Lensify ships in four distribution channels. Pick the one matching your tool. You can install more than one — they share the same engine, so updates flow through automatically.

Channel 1 — Claude Code or Cowork plugin

Step 1. Download lensify.plugin (a zipped archive with a custom extension).

Step 2. Install in your tool:

  • Cowork (desktop): drag-and-drop the .plugin file into the chat, then click Save plugin on the preview card.
  • Claude Code (CLI): run claude plugin install lensify.plugin from the directory where you saved the file.

Step 3. Files land at:

  • macOS: ~/Library/Application Support/Claude/plugins/lensify/
  • Linux: ~/.local/share/claude/plugins/lensify/
  • Windows: %APPDATA%\Claude\plugins\lensify\

Step 4. Restart your tool. The plugin is now active. You'll see SessionStart hook additional context: Lensify dedup is active when a new conversation opens — that's the confirmation.

What this enables: all five hooks, the /lensify, /lensify compact, and /lensify stats slash commands, the statusline, plus auto-scan capability. The full experience.

Channel 2 — MCP server (Cursor, VS Code Copilot Chat, Codex, Gemini CLI, …)

Step 1. Clone the repo (or unzip lensify-mcp.zip):

git clone https://github.com/agenticailab01/lensify ~/lensify
cd ~/lensify
python3 -c "from mcp_server.server import SERVER_INFO; print(SERVER_INFO)"
# expected: {'name': 'lensify-mcp', 'version': '0.15.0'}

Step 2. Add to your tool's MCP config. Locations vary:

ToolConfig file
Cursor.cursor/mcp.json (project) or ~/.cursor/mcp.json (global)
VS Code Copilot Chat.vscode/mcp.json or workspace settings
Claude Desktop~/Library/Application Support/Claude/claude_desktop_config.json
Gemini CLI~/.config/gemini-cli/mcp.json
Codex / OpenCode / Trae / Kiro / AntigravityTool-specific (check docs)

Step 3. Paste this snippet (adjust cwd to your clone path):

{
  "mcpServers": {
    "lensify": {
      "command": "python3",
      "args": ["-m", "mcp_server"],
      "cwd": "/Users/you/lensify"
    }
  }
}

Step 4. Restart the MCP servers in your tool (Cursor: Settings → MCP → reload; VS Code: Command Palette → "MCP: Restart Servers"). The three tools lensify_scan, lensify_compact, and lensify_stats should appear in your tool's MCP tool picker.

Channel 3 — Standalone CLI (Aider, GitHub Copilot CLI, scripts, CI)

Option A — pip install (once published to PyPI):

pip install lensify
lensify --version
# expected: lensify 0.15.0
lensify .

Option B — from a clone (works today):

git clone https://github.com/agenticailab01/lensify ~/lensify
echo 'alias lensify="python3 ~/lensify/skills/lensify/scripts/scan.py"' >> ~/.zshrc
source ~/.zshrc
lensify --version

Both yield the same lensify command. The plugin/MCP install paths and the CLI install path are independent — you can have all three on one machine.

Channel 4 — AGENTS.md write mode (any tool that reads context files)

Already have the CLI installed? You can use AGENTS.md mode right away. It's not a separate install — it's a flag on the CLI:

lensify . --install-agents-md          # writes AGENTS.md
lensify . --install-agents-md CLAUDE.md
lensify . --install-agents-md GEMINI.md
lensify . --install-agents-md .cursorrules

The capsule lands inside the target file wrapped in idempotent <!-- lensify-begin --> / <!-- lensify-end --> markers. Re-running replaces only the marked block; your other content stays.

Suggested workflow: add a Makefile target so the file refreshes on demand:

lens:
	lensify . --install-agents-md

Verify it works

Plugin (Claude Code / Cowork)

# In your chat, type:
/lensify stats
# You should see a JSON report. If you see a "command not found" error,
# the plugin didn't install — re-check Step 4 above.

MCP server

# From a terminal at the lensify clone:
echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' \
  | python3 -m mcp_server
# Expected output: a JSON-RPC response with serverInfo.

CLI

lensify --version           # → lensify 0.15.0
lensify . --no-git          # scan current dir
ls lensify-out/             # LENS.html, LENS.capsule.md, lens.json

AGENTS.md mode

lensify . --no-git --install-agents-md
grep -c "lensify-begin" AGENTS.md   # → 1

Uninstall / cleanup

Lensify is designed to be cleanly removable. Nothing in your project files changes unless you explicitly used --install-agents-md. Below, the cleanup for each channel.

Uninstall the plugin (Claude Code / Cowork)

Cowork: open Settings → Plugins → find lensify → click Remove.

Claude Code:

claude plugin uninstall lensify
# Or manually:
rm -rf "~/Library/Application Support/Claude/plugins/lensify"   # macOS
rm -rf ~/.local/share/claude/plugins/lensify                   # Linux

The hooks immediately stop firing on the next session. No restart of your OS required, just close your chat and start a new one.

Uninstall the MCP server

Step 1. Remove the lensify entry from your tool's MCP config. Other MCP servers in the file are unaffected.

Step 2. Reload MCP servers in your tool (Cursor: Settings → MCP → reload; VS Code: "MCP: Restart Servers"). The three lensify tools disappear from your tool picker.

Step 3. Delete the source clone if you want:

rm -rf ~/lensify

Uninstall the CLI

If installed via pip:

pip uninstall lensify
which lensify   # should now return nothing

If installed via alias / clone:

# Remove the alias line from your shell rc
sed -i '/alias lensify=/d' ~/.zshrc   # or .bashrc
rm -rf ~/lensify

Remove the AGENTS.md capsule block

The capsule lives between the two markers in your context file. You have three options:

Option 1 — keep the file, remove just the capsule block (recommended if you have custom content above/below):

# macOS / Linux
sed -i '' '/<!-- lensify-begin -->/,/<!-- lensify-end -->/d' AGENTS.md   # macOS
sed -i '/<!-- lensify-begin -->/,/<!-- lensify-end -->/d' AGENTS.md      # Linux

Option 2 — delete the file entirely:

rm AGENTS.md

Option 3 — leave it alone. Without the CLI to refresh it, the capsule simply becomes stale. Nothing breaks.

Clean up persistent data

Three locations might contain Lensify data. Wipe whichever you want:

LocationContentsCommand
~/.lensify/ Lifetime stats counters (no PII) rm -rf ~/.lensify
<project>/.lensify-memory/ Cross-session memory entries (per-project) rm -rf .lensify-memory
<project>/lensify-out/ Last scan artefacts (LENS.html, capsule, session state) rm -rf lensify-out
One-liner full cleanup (after uninstall): 
rm -rf ~/.lensify ~/lensify
find ~ -type d \( -name ".lensify-memory" -o -name "lensify-out" \) \
       -prune -exec rm -rf {} +

Soft-disable without uninstalling

If you want to keep Lensify installed but temporarily silent (e.g. for one project where it's getting in the way):

VariableEffect
export LENSIFY_DEDUP=0.*/lensify calls.
export LENSIFY_STATS=0Stops writing to ~/.lensify/stats.json.
export LENSIFY_MEMORY=0Stops cross-session memory.
export LENSIFY_COMPRESS_OUTPUT=0Stops output compression only.

Unset the variables to re-enable. Nothing else changes — no plugin files moved, no data lost.

Verify uninstall

Quick checks that Lensify is fully gone:

which lensify                            # nothing
ls "~/Library/Application Support/Claude/plugins/" | grep lensify   # nothing
ls ~/.lensify 2>/dev/null                # No such file or directory
grep -r "lensify-begin" .                # no markers in your project files

Running your first scan

From inside Claude Code or Cowork:

/lensify                     # scan the current project
/lensify compact         # mid-session: reclaim 8-25k tokens
/lensify stats           # lifetime savings report

From the CLI:

lensify .                                    # scan current dir
lensify . --tier T2                          # force a tier
lensify . --capsule-only                     # skip HTML
lensify . --no-git                           # skip git hotspots
lensify . --output /tmp/lens                 # custom output dir
lensify . --install-agents-md GEMINI.md      # write to context file

Reading the output

The capsule sections

Every capsule starts with these core sections (the exact mix depends on the tier and which frameworks were detected):

SectionWhat it shows
## SUMMARYProject kind, primary language, file count, LOC
## ENTRYMain entry points (main.py, app.py, cli.py, …)
## MODULESTop-level directories with inferred purpose
## SYMBOLSMost-imported public signatures (functions, classes)
## CONVENTIONSDetected tools (Black, Ruff, pytest, pre-commit, …)
## HOTSPOTSFiles with the most git churn in the last 90 days
## RISKSStub files, dead modules, possible smells — confidence-tagged

Plus one section per detected framework — for example, on an AI/ML project you might see ## TORCH, ## TRANSFORMERS, ## CHAINS, ## PINECONE, ## MLFLOW, etc., all in the same scan.

Sample capsule output

# SUMMARY

Python web API in Python; 312 files, 18,450 LOC.

## ROUTES
- `GET /users`  (api.py:14)
- `POST /users`  (api.py:23)
- `DELETE /users/{id}`  (api.py:34)

## SQLALCHEMY
- model `User` — class User(Base) → table users · 4 cols  (models.py:6)
- model `Post` — class Post(Base) → table posts · 5 cols  (models.py:18)
- engine `engine` — create_engine(postgresql://***@host/db)  (db.py:7)
- relationships: User→Post, Post→User

## TRANSFORMERS
- model `tok` — AutoTokenizer ← `distilbert-base-uncased`  (ml.py:14)
- model `model` — AutoModelForSequenceClassification ← `distilbert-base-uncased`  (ml.py:15)
- trainer `trainer` — Trainer  (ml.py:18)

## PINECONE
- create `docs` — create_index('docs', dim=1536, metric='cosine')  (rag.py:8)
- index `idx` — Index('docs')  (rag.py:12)
- indexes referenced: docs
- ops: upsert×3, query×8

Every entry includes (path:line) coordinates and a confidence tag (EXTRACTED, INFERRED, or AMBIGUOUS) so your agent calibrates trust appropriately.

Adaptive tiers

Lensify picks the right depth automatically. You almost never need to override.

Tier Trigger Capsule budget Use case
T1 Sketch < 50 files · < 5k LOC · single language 500 tokens Quick scripts, demos
T2 Atlas 50–1,000 files · 5k–100k LOC · multi-module 2,100 tokens Most real projects
T3 Compass > 1,000 files · monorepo markers · 5+ top-level dirs 3,600 tokens Monorepos, platforms

Override with --tier T1|T2|T3 or hint in chat: "quick summary" → T1, "onboard me" → T2, "all services" → T3.

Session hooks (Claude Code only)

Five hooks fire during a Claude Code session. They compound — savings stack across the session.

Hook Event What it does
dedup_hook PreToolUse:Read Flags repeated reads of the same file. ~25% savings on long sessions.
activity_hook PostToolUse:Edit / Write / Bash Tracks session state. Refreshes the session capsule every 5 turns.
inject_hook UserPromptSubmit Injects only the relevant capsule sections per prompt. ~60% savings.
compress_hook PostToolUse:Bash / WebFetch Deterministic compression of long tool outputs (HTML, JSON, logs, traces).
memory_loader SessionStart Loads cross-session memory of overlapping work.
Cowork limitation: only SessionStart fires in Cowork. The other four hooks need Claude Code's CLI hook surface. The scan engine, capsule generation, and compactor still work in Cowork — just without the in-session savings.

Mid-session compaction

Long sessions eat context. The compactor reclaims 8–25k tokens in seconds:

/lensify compact

This generates a WORKING_CONTEXT.md summarising:

  • Which files you actually touched
  • Bash commands you ran (and their results)
  • Tests that passed/failed
  • Decisions made + open threads
  • An optional LLM-enhanced paragraph if ANTHROPIC_API_KEY is set

Then run /clear in your tool and paste WORKING_CONTEXT.md at the top of the next session. You resume with the same shoulder-context but a fresh token budget.

Cross-session memory

Each compaction also writes a memory entry to <project>/.lensify-memory/. At the next session start, the memory loader hook pulls the most relevant prior entries — scored by recency × module overlap — and surfaces them as additional context. Max 50 entries per project, LRU eviction.

Opt out: export LENSIFY_MEMORY=0.

Token economics

Where the savings come from:

Stage Before Lensify With Lensify Approximate savings
Orientation 8,000–20,000 tokens reading 20+ files One capsule, 800–3,600 tokens 70–90%
Repeat reads Each re-read costs the full file Dedup flag, ~0 tokens ~25% on long sessions
Per-prompt re-injection Full capsule every prompt Only relevant sections ~60%
Long tool outputs Raw HTML / JSON / log dump Compressed summary + handle variable (often 80%+)
Mid-session compaction Manual /clear loses everything WORKING_CONTEXT.md preserves continuity 8k–25k per compaction

CI enforces 17 performance + security budgets on every change. Hook subprocess startup < 250 ms. Hook output ≤ 500 tokens per event. Adding adapters can't regress any of these.

Security & governance

Lensify is the most security-hardened tool in its category. Every persistent surface has documented opt-outs; every dangerous primitive is banned by static analysis.

What's banned in shipped code (CI-enforced)

  • exec() · eval() · __import__()
  • pickle.loads() · marshal.loads()
  • shell=True · os.system()
  • Outbound HTTP outside llm_client.py (single allowlisted endpoint)

Opt-out env vars

VariableEffect
LENSIFY_DEDUP=0Disable ALL hooks
LENSIFY_STATS=0Disable lifetime stats
LENSIFY_MEMORY=0Disable cross-session memory
LENSIFY_COMPRESS_OUTPUT=0Disable output compression
LENSIFY_USER_ADAPTERS=1Opt IN to user-defined adapters (off by default)
LENSIFY_MAX_READ_BYTES=NChange per-file read cap (default 1 MB)
LENSIFY_STATS_HOME=pathChange where stats live

Data handling

  • Stats: ~/.lensify/stats.json. Plain JSON counters, no PII, no file contents.
  • Memory: <project>/.lensify-memory/. Plain JSON, max 50 entries per project, LRU eviction.
  • Session state: <project>/lensify-out/state.json. Wiped between sessions.
  • Outbound network: single optional call to api.anthropic.com only if --llm is used AND ANTHROPIC_API_KEY is set.

See SECURITY.md for the full threat model and vulnerability reporting process.

Extending it — write your own adapter

The adapter SDK is intentionally small. Copy the template to start:

cd skills/lensify/scripts/frameworks
cp -r _template _myframework
mv _myframework/template.py _myframework/myframework.py
# edit: rename class, update regexes
# register in manifest.json

Each adapter is ~80–120 LOC and ships with tests. The SDK enforces five rules:

RuleWhat
R1Hook scripts never import frameworks/*
R2Adapter modules stay small (~80–120 LOC)
R3detect() is O(1) — never opens files
R4extract() opens only files matching your framework's signature
R5capsule_section() respects budget_tokens

Rules R1 and R3 are enforced by CI. R2/R4/R5 are review conventions.

For org-specific frameworks you don't want to upstream, drop adapters into <project>/.lensify/frameworks/*.py. They're loaded automatically per-scan once you opt in with LENSIFY_USER_ADAPTERS=1.

FAQ

Does it work on my JS/TS / Go / Rust project?

The base scan (file walk, language detection, symbols) works on JS, TS, Go, Java, Rust, Ruby, PHP, C/C++, and ~20 other languages. The 30 framework-specific adapters are mostly Python-focused right now, with Vue SFC + Tailwind + Docker Compose covering the JS/web side. JS/TS framework adapters (Next.js, Astro, SvelteKit, NestJS) are on the roadmap.

Will it slow down my Claude Code session?

Hook subprocess startup is capped at 250 ms cold (typically 20–30 ms warm). Hook output is capped at 500 tokens per event. Both caps are CI-enforced. The scan itself runs on-demand, not per-prompt.

Does it send my code anywhere?

No, unless you explicitly run /lensify compact --llm AND have ANTHROPIC_API_KEY set. Even then, only the session activity summary (files touched, commands run) is sent — never file contents.

Is the capsule different from a README?

A README tells humans what the project does. The capsule tells your agent what the project contains: routes, models, training loops, vector indexes, deployments, etc. Different audience, different output.

What if my framework isn't covered?

The base scan still produces a useful capsule (entry points, modules, symbols, hotspots, risks). You also get less framework-specific noise. Add a custom adapter in ~100 LOC if you want richer output for that framework.

Can I disable everything and just use the scan?

Yes — export LENSIFY_DEDUP=0.*/lensify invocations.

Why not just use Cursor's @codebase or Sourcegraph Cody?

Those tools do semantic vector search — they need an embedding model, a vector store, and continuous indexing. Lensify does structural extraction — deterministic, fast (sub-second), cheap, and framework-aware. The two are complementary: Lensify for orientation, semantic tools for in-depth search.

Is it free?

Yes — MIT licensed. No subscription, no telemetry sent off-device.
